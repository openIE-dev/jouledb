JouleDB v1.0.0

Why JouleDB: Prior Art, Architecture, Evaluation & Licensing

Data movement across disconnected infrastructure silos—OLTP database, columnar warehouse, vector index, property-graph engine, container daemon, and external LLM weight servers—consumes orders of magnitude more joules and tail latency than arithmetic inside an ALU. JouleDB consolidates transactional storage, hybrid retrieval, and sub-1-bit .jsyn neural execution onto a single Copy-on-Write Serializable Snapshot Isolation (SSI) substrate written in Rust (41 workspace member crates / 746,915 LOC in crates/, v0.12.0 pre-1.0 preview, 41 / 41 deny(clippy::unwrap_used)).

This chapter states the prior art JouleDB builds on, where established systems outperform JouleDB, the exact 1..15 hyperdimensional computing (HDC) primitives, benchmark protocols (including where Hits@1 drops sharply relative to Hits@10), and licensing/packaging history.

1. The Core Problem & Prior Art: Data Movement vs. Arithmetic Energy

Energy-aware data management and low-bitwidth inference build on a deep systems literature:

  • Whole-System Sorting & I/O Energy — JouleSort (Rivoire, Shah, Ranganathan & Kozyrakis, SIGMOD 2007): Introduced whole-system joules-per-record sorting benchmarks and showed that storage I/O, DRAM traffic, and system base power dominate raw CPU arithmetic.
  • Energy-Proportional Data Systems (Harizopoulos, Shah, Meza & Ranganathan, CIDR 2009): Framed software-level query energy optimization and hardware energy proportionality as first-class database architecture objectives.
  • Why “Fastest = Most Energy-Efficient” on Conventional Servers (Tsirogiannis, Harizopoulos & Shah, SIGMOD 2010): Demonstrated experimentally across DBMS operators that on conventional servers with high static/idle socket power, the fastest execution plan is almost always the most energy-efficient plan, because keeping the package awake longer outweighs small dynamic-power differences between join or scan operators.
  • Ternary Weight Compression — BitNet b1.58 (Ma et al., 2024): Showed that ternary ${-1, 0, +1}$ weight matrices replace floating-point multiply-accumulate (FP16 MAC) with integer addition while drastically reducing weight-fetch memory bandwidth.

Where Tsirogiannis et al. (2010) Governs — and Where JouleDB Operates Differently

Inside a single relational scan, join, or aggregation on an active server, Tsirogiannis et al.’s result holds directly for JouleDB: morsel-driven 2,048-row vectorization, ZoneMap cold-granule skipping (97.96% skip on ClickBench-style filters), and SIMD POPCNT save energy primarily by minimizing wall-clock time.

JouleDB targets three cross-layer regimes outside single-engine SQL plan selection:

  1. Eliminating Cross-Service Serialization & IPC: Collapsing a multi-service stack (PostgreSQL -> JSON/Arrow -> Vector Store -> Graph Engine -> HTTP LLM Server) into one shared-memory SSI snapshot removes repeated UTF-8 JSON marshaling, socket round-trips, and duplicated OS page caches.
  2. Multi-Tier Algorithmic Complexity Cascade: Rather than running a fixed-cost neural pass on every request, JouleDB routes queries through an escalating cost cascade: LSN LangCache (~95 nJ est) -> Engram O(1) exact lookup (~220 nJ est) -> TriModal RRF (BM25 ⋈ RaBitQ 1-bit POPCNT ⋈ HDC, ~1–10 µJ) -> .jsyn Living Bitplanes (mJ–J). Short-circuiting repeated or exact factual lookups at O(1) avoids waking GPU/NPU rails at all—reducing work by $10^3\times$–$10^6\times$ rather than tuning operator watts by 10%.
  3. Sub-1-bit .jsyn (LittleBit-2 ⊕ Sakana SVF) Memory-Traffic Reduction (Within Rank Limits): Compressing compact bidirectional encoders (all-MiniLM-L6-v2-LittleBit at 0.44 BPW, 22.2× smaller) preserves 0.9441 cosine similarity, whereas ultra-low 0.02–0.17 BPW settings severely degrade autoregressive LLMs (cos = 0.27–0.45) and are not drop-in LLM replacements.

When to Choose DuckDB, PostgreSQL, ClickHouse, or vLLM Instead of JouleDB

  • Use DuckDB for embedded analytical SQL over local Parquet/Arrow datasets in Python, R, or CLI scripts.
  • Use ClickHouse for multi-terabyte or petabyte distributed event/observability warehousing.
  • Use PostgreSQL + pgvector when you need battle-tested relational OLTP, full PostgreSQL extension compatibility, mature logical replication, or a managed cloud SLA.
  • Use vLLM or llama.cpp when your primary workload is high-concurrency open-ended text generation over multi-GPU BF16/FP8/Q4 models without database state coupling.

4. Evaluation Protocols, Metrics & Orthogonal Evidence Classes

4.1 Energy Evidence Taxonomy (measured_j ⊥ reported_j ⊥ est_j ⊥ unmetered)

JouleDB enforces four mutually orthogonal energy classes—values from distinct classes must never be summed, averaged, or relabeled:

  • measured_j (External Inline Meter): Physical DC rail shunt (INA238 / INA3221) or calibrated AC wall analyzer. JouleDB software alone never emits measured_j unless an external hardware meter is attached.
  • reported_j (On-Chip / OS Hardware Counter): Kernel/PMU counters on bare-metal hosts: Apple Silicon IOReport / proc_pid_rusage(RUSAGE_INFO_V6).ri_energy_nj on macOS and /sys/class/powercap/intel-rapl* (Intel & AMD RAPL) on Linux. Socket/package counters reflect co-tenant load unless isolated via per-PID counters or idle-drift checks.
  • est_j (Analytical Silicon Ledger): Deterministic instruction + cache/DRAM byte-movement cost model (crates/joule-energy, e.g., ~95 nJ LangCache, ~220 nJ Engram) used for sub-microsecond single-operator attribution or inside WASM / unprivileged containers.
  • unmetered (joules: null): Exact wall-clock nanoseconds, CPU time, and byte counts when no hardware energy counter is readable without root.

4.2 WN18RR / PathHD Filtered Link-Prediction Protocol & Hits@1 vs. Hits@10

Knowledge-graph link prediction is evaluated on WN18RR (40,943 entities, 11 lexical relations, 86,835 train / 3,034 validation / 3,134 test triples) under the standard filtered ranking protocol (Bordes et al., NeurIPS 2013):

  1. For each test triple $(h, r, t)$, evaluate both tail corruption $(h, r, t’)$ and head corruption $(h’, r, t)$ across all $40,943$ entities (6,268 ranked queries total) with zero gradient updates.
  2. Remove every corrupted candidate $(h, r, t’) \neq (h, r, t)$ that appears in train ∪ valid ∪ test (filtered setting) so known true facts do not artificially demote the ground-truth target.
  3. Break ties deterministically (strict/mean rank, never optimistic rank-1 ties) and report both Hits@1 and Hits@10 alongside MRR:
